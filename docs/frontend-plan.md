# План за frontend на UniCloud Auto Judge

Статус: студентският, преподавателският и административният интерфейс са
реализирани в branch `feature/judge-web`. Подготвени са frontend container,
reverse proxy и HTTPS конфигурация. Публичното публикуване чака домейн, сървър
и production регистрация в Portal; не е извършено.

Текущите оставащи задачи, приоритети и критерии са в
[Оставаща работа и следващи версии](remaining-work.md). Етапите по-долу описват
първоначално приетия обхват, а не списък само с незавършена работа.

## Цел и първа версия

Да реализираме браузърен интерфейс върху съществуващия API: вход през UniCloud
Portal, управление на задания и тестове, предаване на решения и преглед на резултати.
Първата версия обслужва STUDENT, TEACHER и ADMIN.

Извън първата версия: курсове, факултети, DEAN, регистрация и пароли в Judge,
управление на Portal роли, AI помощник, онлайн изпълнение на произволен код,
изтегляне на предаден код и разширен редактор тип IDE.

## Текуща основа

- API има задания, тестове, предавания, резултати, класиране и администриране на потребители.
- Portal SSO използва PKCE и сървърни Redis сесии. Browser API заявките използват cookie и CSRF.
- Успешният browser вход връща към `/assignments`; `/api/users/me` остава default
  при API конфигурация без frontend.
- Локалните API, PostgreSQL, Redis и MinIO са стартирани; API е на порт 8081.
- Проверени са здравето на зависимостите, реален Portal вход и завършен
  сценарий с frontend container и локалния worker.
- Worker е стартиран отделно от Compose чрез локалния launcher.
- При разминаване със старите поетапни документи контролерите, DTO и текущото
  поведение на приложението са основата за frontend договора.

## Технологии и организация

Използваме React, TypeScript, Vite, React Router, TanStack Query, семантични HTML
контроли и общ CSS. Интерфейсът е на български; пълната интернационализация
остава бъдещо подобрение.

Кодът е в `apps/judge-web/`, с модули за auth, assignments, submissions, results
и administration, общ API клиент и споделени компоненти. Типовете се генерират
от проверена OpenAPI спецификация; CI открива разминаване с backend договора.
Това не отменя обработката на HTTP статуси, null стойности и домейн грешки.

## Етап 0 — Отделяне на основата и приемателен сценарий

1. Завършваме backend PR за SSO и API–worker поправките; frontend промените се
   отделят в нова branch/PR. Ако backend PR още е отворен, записваме зависимостта
   и отделяме frontend diff спрямо него. Сливането остава отделно действие.
2. Проверяваме браузърен вход с тестовите STUDENT, TEACHER и ADMIN потребители
   и необходимите Portal permissions. ADMIN трябва да присъства в allowlist.
3. Потвърждаваме API ограниченията: студентът предава решения, преподавателят
   управлява своите задания, администраторът има общ преглед.
4. Подготвяме демонстрационно задание с публичен и скрит тест чрез API/UI.

Критерий: известни са работещите тестови идентичности и точният сценарий
„преподавател публикува → студент предава → worker оценява → резултат“.
Пароли, Portal тайна и worker credential не се включват във frontend build.

## Етап 1 — Основа на приложението

1. Създаваме React/TypeScript приложението, команди за dev, build, lint и typecheck.
2. Добавяме основна навигация, responsive оформление, начална страница за вход,
   състояния за зареждане, празни списъци, грешки и недостъпни страници.
3. Добавяме общ API клиент за cookie сесии и ProblemDetail грешки.
4. Настройваме Vite proxy за `/api`, `/auth`, `/oauth2` и `/login/oauth2` към
   `http://localhost:8081`. Frontend е на `http://localhost:5173`.
5. Използваме callback `http://localhost:5173/login/oauth2/code/portal`.
   Началото на входа и callback минават през един и същ браузърен origin.
   Portal staging допуска този адрес; production изисква точна регистрация.

Критерий: приложението се изгражда успешно и достъпва реалния API през proxy.
Фокусът, етикетите на формите и основните действия работят с клавиатура.

## Етап 2 — SSO и потребителска сесия

1. „Вход през UniCloud“ отваря `/oauth2/authorization/portal`.
2. Backend получава настройка за фиксиран вътрешен адрес след успешен вход,
   например `/assignments`. Запазваме сегашното поведение като default за
   стартиране без UI; не приемаме произволен redirect адрес от браузъра.
3. След вход зареждаме `/api/users/me` и показваме навигация според ролята.
4. Получаваме CSRF header и token от `/auth/csrf`; изпращаме ги при
   POST, PUT, PATCH и DELETE. Презареждаме CSRF след вход и смяна на сесията.
5. Изходът е `POST /auth/logout`, след което изчистваме потребителския кеш.
   Той прекратява Judge сесията, а Portal сесията може да остане активна.
6. При 401 предлагаме нов вход и запазваме несекретните данни от незавършена
   форма, когато е възможно. При 403 показваме отказан достъп; при 503 от Portal
   показваме временна недостъпност без redirect цикъл.

Критерий: вход, reload, изход и изтекла сесия работят в реален браузър.
Проверяваме Secure cookie поведението на localhost и през proxy. Frontend няма
Portal токени в localStorage/sessionStorage; backend проверява всички права.

## Етап 3 — Студентски интерфейс

1. `/assignments`: списък с пагинация и поддържаните от API филтри.
2. `/assignments/:id`: условие, срок в локалната часова зона, максимален брой
   точки и видими публични тестове. Описанията не се изпълняват като HTML.
3. Форма за един source файл и език. Поддържаме десетте езика от API договора;
   проверяваме разширение и размер според конфигурацията на средата. Backend
   остава окончателната проверка, включително за крайния срок.
4. Предаваме multipart заявка с `Idempotency-Key`. Повторение на същото
   предаване запазва ключа и съдържанието; ново решение получава нов ключ.
5. `/submissions`: собствена история с пагинация и филтри.
6. `/submissions/:id`: статус, резултат и достъпните данни за тестовете.

Критерий: студент намира задание, предава файл и вижда потвърждение и история.
Покрити са невалиден файл, изтекъл срок, мрежово прекъсване и повторно натискане.
Приетото предаване не се представя като вече оценено.

## Етап 4 — Worker и реални резултати

1. Настройваме отделния worker token, включваме API–worker транспорта и
   стартираме worker с нужните toolchain images и Redis настройки. Достъпът до
   source файлове и тестове минава през частния API, без S3 credentials в worker.
2. При PENDING/RUNNING обновяваме резултата периодично, например през 3 секунди,
   с ограничени повторения при грешки и пауза при скрит таб. Не е нужен WebSocket.
3. Спираме polling при COMPLETED, FAILED и CANCELLED. Различаваме статуса
   на обработка от verdict, например WRONG_ANSWER или COMPILATION_ERROR.
4. Null оценка означава „няма налична оценка“, а не нула. Не показваме
   измислени compiler diagnostics или данни за скрити тестове, които API не връща.
5. Добавяме класиране за задание чрез съществуващия leaderboard endpoint.

Критерий: реални правилно и грешно решения стигат до крайни резултати.
Проверяваме и compilation error, чакане при спрян worker и възстановяване.
Не правим ново предаване само защото проверката на статуса е прекъснала.

## Етап 5 — Преподавателски интерфейс

1. Създаване и редактиране на задание: условие, точки и срок.
2. Управление на публични и скрити тестове и точки. Изпълнителните ограничения
   днес са worker defaults; лимити по задание са отделна задача PROD-03 в backlog.
3. Публикуване с ясни грешки при липсващи тестове или несъвпадащи точки.
4. Изрично потвърждение при нова ревизия; показваме връщането към DRAFT
   и нуждата от повторно публикуване. Презареждаме копираните тестове.
5. Архивиране и допустимо изтриване според ограниченията за запазена история.
6. Преглед на предавания и резултати за собствените задания.

Критерий: преподавател създава, тества чрез студентския сценарий и архивира
задание. Старите резултати остават свързани със съответната ревизия.

## Етап 6 — Администрация

1. Списък и търсене на локално създадените/синхронизирани Judge потребители.
2. Преглед на профил и активиране/спиране на достъпа до Judge.
3. Преглед на всички задания и свързаните предавания.
4. В Portal режим не предлагаме редакция на роли или създаване на Portal
   акаунт през Judge. Наличният списък не е каталог на всички Portal потребители.

Критерий: административните операции работят, а backend отказва същите
заявки от студент или преподавател независимо от скритите UI контроли.

## Етап 7 — Проверки и доставка

1. Автоматизираме критичните browser сценарии с Playwright: роли, предаване
   и безопасно повторение, обновяване на резултат и промяна на задание.
2. Изолираните CI проверки използват контролирани тестови идентичности/OIDC
   среда. Допълнително проверяваме реалния Portal staging вход; не разчитаме
   общият staging да е винаги достъпен за всеки CI build.
3. Тестваме backend промяната на адреса след вход и запазването на
   CSRF/сесиите. За конфигурационните промени изпълняваме целеви smoke проверки.
4. В CI изпълняваме lint, typecheck, build и избраните функционални тестове.
5. Подготвяме frontend container и reverse proxy: UI и API са на един origin;
   API/auth маршрутите се обслужват преди SPA fallback. Production е с HTTPS.
6. Документираме старт, променливи, портове и приемателния сценарий. Публикуване
   в production и регистрация на production callback са отделни стъпки.

Критерий: друг разработчик стартира средата по документацията и изпълнява
целия сценарий от публикуване на задание до преглед на реален резултат.

## Последователност на PR-ите

Първоначален план за разделяне на работата; описаните функционалности вече са
в текущия working tree. Окончателното оформяне за review е задача REL-01 в
[backlog](remaining-work.md), а не повторно реализиране на тези етапи.

1. Frontend основа, SSO, навигация и read-only списък със задания (етапи 1–2).
2. Студентски предавания, история, worker демонстрация и резултати (етапи 3–4).
3. Преподавателски задания, тестове и ревизии (етап 5).
4. Администрация (етап 6).
5. Финални E2E сценарии и deployment конфигурация (етап 7).

Всеки PR включва проверките за своя сценарий; те не се отлагат изцяло за
последния PR. Първата демонстрация е SSO вход → профил → списък със задания.
