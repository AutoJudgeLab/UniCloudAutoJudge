## 1. Какво се демонстрира пред преподавателя

**Бизнес цел:** от публичен интернет адрес преподавателят публикува задание и тестове, студент предава код, получава уникално потвърждение, кодът **реално се изпълнява**, вижда се оценка и история/класация; при пик приемането остава отделено от оценяването.

Не представяйте локални unit/Docker тестове или Redis доставка като доказателство за завършен end-to-end процес. При прегледа на `main` на 16.11.2026 г. `judge-worker` още е празен, но **SE2 е предоставил отчет за локално разработен Java Worker и Docker sandbox**. Той докладва 37 unit и 10 интеграционни теста с истински Docker, без реален Redis/Judge API end-to-end, remote branch/PR или публично потвърдено внедряване. Документираният k6 smoke с 4 заявки измерва само приемането.

**Документални факти:** [verification](../verification.md) отчита локално 129 теста без грешки и k6 проба 4/4 HTTP 201 от 2 виртуални потребителя, клиентски p95 31 ms; това е измерване на приемането, **не на автоматичното оценяване**. Времената са за конкретен локален smoke, не за публично SLO, 1500 студенти или хиляди заявки в секунда. Не се твърди, че тестовете са повторени на 16.11.

**Нов независим от горните числа екипен отчет (SE2, 16.11):** 37 unit теста, 10 интеграционни теста с истински Docker (общо 47), успешно локално Java оценяване (`ACCEPTED`, `WRONG_ANSWER`, `COMPILATION_ERROR`, `RUNTIME_ERROR`, `TIME_LIMIT_EXCEEDED`, `MEMORY_LIMIT_EXCEEDED`) и отхвърлени опити за мрежов достъп, запис по файловата система и неограничено създаване на нишки. Unit тестът с 40 едновременни задачи използва mock зависимости и не доказва масово натоварване. Обхватът е **Java**, Python/C/C++ профилите са изключени. Отчетът **не означава** успешен интеграционен тест на Worker с истински Redis/Judge API.

## 3. SLO: какво представя PM пред Ректора

Единственият действащ чернови източник е [slo-sla.md](../slo-sla.md). Неговите **предложени**, още непотвърдени чрез представително натоварване показатели са:

| Показател | Предложена цел | Какво трябва да се докаже |
| --- | --- | --- |
| API наличност | 99.5% от допустимите заявки за календарен месец | Реални/синтетични измервания в определена среда; време-бюджетът за 30 дни е ориентировъчно 216 мин. |
| Приемане на решение | p95 ≤ 500 ms | Външно наблюдавано време за приети валидни заявки при договорен профил |
| Приемане при пик | p99 ≤ 2 s | Отчет с обхват на пика и размери на файловете |
| Потвърдени, но изгубени решения | Цел: 0 | ID + изходен файл + DB metadata са възстановими при договорените откази; необходими са backups и restore проверки |
| Време до **оценяване** | **ОЩЕ НЕДОГОВОРЕНО** | Да се предложи **отделна** измерима цел след baseline на реалния worker |

Защитимо PM обяснение: „Приемане на решение“ е отделно от „готова оценка“. При пик оценяването може да чака в опашка; това не трябва да води до загуба на потвърдено предаване. Ректорските цели от 100% наличност, „хиляди решения/секунда“ и оценка под 0.5 секунди **не са установени способности**.

При изчерпан бюджет за грешки: пауза на незадължителни нови функции; анализ на инцидента; възстановяване и тест; отчет с коригиращи действия. Не се декларира договорен SLA към реални клиенти.

## 5. Протокол за натоварване преди демото

- [ ] DevOps и PM са записали профила: брой студенти, равномерни заявки, пик в последните 10 минути, брой/размер на файловете и продължителност.
- [ ] За всяко успешно `201` е проверено наличието на съответния `submissionId`, изходен файл и metadata; опашката не е единствено доказателство.
- [ ] Записани са p50/p95/p99, успешни и неуспешни заявки, 4xx/5xx, пиков backlog, време до оценка и ресурсна консумация.
- [ ] Измерен е резултатът при вдигане на товара и възстановяването след него.
- [ ] Ако се тества отказ на Redis или на worker, записана е съдбата на потвърдените решения и повторенията.
- [ ] Ясно е посочено дали тестът използва истински worker и публична среда, или е локален инфраструктурен тест.
- [ ] Посочени са машина, версии, квоти и условията; отчетени са ограниченията на извадката.

**Налични към момента доказателства:** `docs/verification.md` отчита локални integration тестове на API и smoke с 4 заявки. Отделният отчет на SE2 потвърждава **локални Docker тестове на Java Worker**, но **не** 1500 конкурентни студенти, истински Redis/Judge API end-to-end или целта за оценяване под 0.5 s. SE2 оценява около 1 s допълнителни разходи за стартиране на контейнер за всеки тест; реалистично SLO за оценяване трябва да се измери и съгласува.

## 6.1. Готов кратък отчет за междинното представяне (17.11.2026)

**Текущ етап:** **частично готов MVP**; има backend основа и отделно **локално реализиран Java Worker/Docker sandbox с 47 успешни теста по отчет на SE2**. В `main` Worker още не е наличен, а двата вътрешни Judge API endpoints/worker identity, истински Redis/Judge API end-to-end, Security review и публична среда предстоят. Това е документална оценка, **не PM приемателен тест**.

**Какво мога да покажа като PM:** [продуктова спецификация](../product-spec-week1.md), [приоритети и блокери](week1-backlog-and-decisions.md), [външни зависимости](week1-integration-agreements.md), настоящата приемателна матрица и [GitHub Issues](https://github.com/AutoJudgeLab/UniCloudAutoJudge/issues). Документите са публикувани, но техническите решения в тях не са едностранно одобрени.

**Какво може да покаже инженерният екип при успешно локално стартиране:** Judge API — вход, създаване/публикуване на задание, upload, `submissionId`, `PENDING`, история и Redis публикация; **SE2 отделно** може да демонстрира истински локален Docker тест на Java Worker с `ACCEPTED`/`WRONG_ANSWER`/ресурсни ограничения, ако разполага с кода и средата. Това **не** е общ end-to-end резултат и не потвърждава, че е демонстрирано на 17.11.

**Какво не показваме като завършено:** **реална оценка, записана през интегрирания Judge API**, публично приет Worker Sandbox/production Security review, публично внедряване, мащабируемост при 1500 студенти, 100% надеждност или фактически нулев разход. Локалният sandbox и Java grader са **разработени и тествани според SE2**, но не са интеграционно приети.

### Минимален говорен сценарий (PM, около 90 секунди)

> „Екип 3 разработва система за приемане и автоматично оценяване на студентски код. При пика в 23:59 ч. разделяме приемането на предаванията от последващото оценяване. Вече разполагаме с backend основа — автентикация, задания и тестове, приемане на решения, PostgreSQL, MinIO и Redis. Допълнително Software Engineer 2 отчита локално реализиран Java Worker с изолирано Docker изпълнение, оценяване, повторни опити и 47 успешни теста, от които 10 с истински Docker. Това е значим напредък, но Worker още не е интегриран с реален Redis и Judge API; вътрешните API endpoints и публикуването/прегледът на кода предстоят. Като PM подготвих продуктовите изисквания, критериите за приемане, SLO предложенията, задачите и междуекипната координация. Остава да потвърдим Java обхвата, да завършим интеграцията, Security review и публичния deployment и да измерим натоварването. Не представяме локалните тестове като доказателство за готов продукт или гарантирано SLO.“

**Резервен вариант:** ако инженерното демо не стартира, представете наличните Java контролери, техническите отчетни доказателства и честния списък на блокерите. Резервният вариант **не се отбелязва като преминат публичен приемателен сценарий**.
